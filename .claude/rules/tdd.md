# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 일부만 적용하지 않는다.

## 프로젝트 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (엔드포인트, 요청/응답 처리)
- 유틸 / 순수 함수
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

경계가 모호하면 **적용 대상으로 간주**한다.

## RED-GREEN-REFACTOR 사이클

### 1. RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 테스트 자체의 버그로 실패했다면 테스트를 고쳐서 다시 RED를 확인한다.

### 2. GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 지금 테스트가 요구하지 않는 기능은 넣지 않는다.
- **신규 + 기존 테스트 모두 통과**하는지 전체를 실행해 확인한다.

### 3. REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **항상 green을 유지**한다. 변경할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 비용이 작으니 생략할 이유가 없고, 단순한 코드가 가장 자주 조용히 깨진다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현에 맞춰져 항상 통과한다. 설계를 이끌지 못하고 실패를 증명하지도 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 훨씬 오래 걸린다. TDD는 속도를 늦추는 것이 아니라 재작업을 줄인다. |
| "삭제하면 낭비다" | 매몰 비용이다. 테스트 없이 쓴 코드는 검증되지 않은 부채이므로 지금 지우는 것이 가장 싸다. |
| "프로토타입이다" | 프로토타입은 프로덕션으로 승격된다. 버릴 코드라면 삭제 비용도 없으니 규칙을 지켜도 손해가 없다. |
